# 新人後台 手機／平板 UIUX 健檢報告

- 檢查對象：`public/admin.html`、`public/css/admin.css`、`public/js/admin.js`、`public/js/seating-plan.js`、`public/js/cropper.js`
- 檢查裝置情境：手機直向（360–430px）、平板直向（768–834px）、平板橫向（1024–1194px）
- 日期：2026-08-23
- 本報告只做診斷，**沒有更動任何程式碼**

---

## 0. 一句話總結

後台的「資訊架構、文案、空狀態、確認流程」做得比一般專案好很多（每個清單都有 Empty State、刪除要打字確認、有 Undo toast、有 skeleton）。
真正的問題集中在 **「這是一個桌機介面被塞進手機」** 這件事上，尤其是四塊：
**① 輸入框字級造成 iOS 自動縮放、② 離線／弱網儲存無回饋且可能靜默遺失、③ 回覆名單在手機是 16 欄橫向表格、④ 排桌工作區的主要 CTA 在手機會捲出畫面且沒有草稿保護。**

| 嚴重度 | 項目數 | 說明 |
|---|---|---|
| P0 阻斷 | 4 | 手機上會直接做不完事、或會掉資料 |
| P1 高 | 5 | 明顯難用、誤觸率高 |
| P2 中 | 9 | 體驗打折，但做得完 |

## 1. P0 — 阻斷級

### P0-1｜所有輸入框字級 < 16px，iOS Safari 一聚焦就自動放大整頁

| 項目 | 內容 |
|---|---|
| **頁面** | 全站所有分頁（最痛：排桌工作區、婚禮小卡、匯入精靈、回覆名單搜尋） |
| **功能** | 所有 `input` / `textarea` / `select` |
| **現況** | `.ad-input`／`.ad-textarea` 15px（`admin.css:167`）、`.ad-filter` 13px（`:372`）、`.sp-search` 12.5px（`:801`）、`.ad-card .ad-input` 12.5px（`:531`）、`.ad-quiz-opt .ad-input` 14px（`:557`）、`.sp-map-row select` 13px、`.sp-preview` 12px。<br>viewport 是 `width=device-width, initial-scale=1.0`，沒有 `maximum-scale`（這是對的，不該鎖），所以 **iOS Safari 只要聚焦字級 <16px 的欄位就會把整頁放大**，放大後版面往右偏、使用者要自己雙指縮回來。排桌工作區的搜尋框每打一次字就發生一次。 |
| **建議** | 1. 把 **所有可輸入元件的 `font-size` 統一提到 16px**（`.ad-input`、`.ad-textarea`、`.ad-filter`、`.sp-search`、`.ad-card .ad-input`、`.ad-quiz-text`、所有 `select`）。<br>2. 如果桌機上覺得 16px 太胖，用 `@media (min-width:900px)` 再降回 13–14px，只讓觸控裝置吃 16px。<br>3. 順手補 `input` 的 `inputmode`（搜尋用 `search`、金額／人數用 `numeric`）與 `enterkeyhint="search"`。 |

### P0-2｜離線／弱網時儲存沒有任何回饋，而且可能靜默掉資料

| 項目 | 內容 |
|---|---|
| **頁面** | 全站（婚禮資訊、當日流程、表單設定、標籤、感謝信、小卡、故事牆、測驗、排桌） |
| **功能** | 所有「儲存」按鈕、所有自動存檔（卡名／圖片標題離開欄位就存） |
| **現況** | `DataStore.saveDoc()`（`common.js:470`）與 `saveSiteFields()`（`:487`）都是 `await setDoc/updateDoc`。<br>Firestore 在離線時 **這個 Promise 永遠不會 resolve**（不是 reject），所以：<br>・`try/catch` 抓不到，**toast 不會出現、也不會出錯誤**；<br>・按鈕沒有 disable、沒有 loading 態，使用者會連按好幾次；<br>・但 `onSnapshot` 的本地樂觀更新會讓 **畫面看起來已經存好了**；<br>・`site-context.js:120` 用 `getFirestore(app)` 預設 memory cache，**沒有開離線持久化** → 使用者關掉分頁，剛剛「看起來存好」的東西就沒了。<br>全站也沒有任何斷網偵測（沒有 `navigator.onLine` / `online`-`offline` 監聽）。 |
| **建議** | 1. **送出時就給狀態**：按下儲存後把按鈕改 `disabled` + 文案換成「儲存中…」，成功才恢復。<br>2. **加逾時**：`Promise.race([setDoc(...), timeout(8000)])`，逾時就跳「網路好像不太穩，這筆還沒送出去」的 toast + 「重試」按鈕（toast 已經支援 `actionLabel`，`admin.js:34`）。<br>3. **加全域斷網橫幅**：監聽 `online`/`offline`，斷線時在 `ad-bar` 下方壓一條「目前離線，改動不會存進去」的細條。<br>4. 評估開 `persistentLocalCache`，至少讓離線期間的改動撐到重新連上。 |

### P0-3｜回覆名單在手機是 16 欄的橫向表格

| 項目 | 內容 |
|---|---|
| **頁面** | 出席回覆 → 回覆資訊 |
| **功能** | 回覆名單 `rsvpTableHtml()`（`admin.js:846`） |
| **現況** | 全開時共 16 欄：標籤／姓名／出席回應／分類／聯絡資訊／人數／葷／素／兒童椅／飲食習慣／喜帖／喜餅／給新人的話／備註／填表時間／刪除。其中三欄是 `min-width:180px`。<br>在 390px 的手機上表格實寬約 1300–1500px，**要左右滑 3–4 個螢幕寬**才看得到「人數／葷／素」，而這恰好是新人最常看的欄位。<br>外層 `.ad-tablewrap{overflow:auto;max-height:70vh}`（`admin.css:409`）→ 手機上是「內層直捲 + 內層橫捲 + 整頁直捲」三層互搶，很容易滑到一半頁面跳走。<br>`th` 是 sticky，但 **姓名那一欄沒有 sticky**，橫滑之後就不知道現在看的是誰。 |
| **建議** | 1. **手機（<900px）改成 Card / List View**：一位一張卡，第一行「姓名 ＋ 出席狀態 pill」，第二行「N 位・葷 X／素 Y・兒童椅 Z」，其餘（聯絡、喜帖、喜餅、留言、備註、時間）收進「展開更多」。桌機維持現在的表格。<br>2. 如果要保留表格，至少把 **姓名欄 `position:sticky; left:0`** 釘住，並拿掉手機上的 `max-height:70vh`（讓它跟著整頁捲，不要三層捲動）。<br>3. 表格容器左右邊緣加漸層遮罩，明示「可以往右滑」。 |

### P0-4｜排桌工作區：手機上「儲存排桌」會捲出畫面，且沒有草稿保護

| 項目 | 內容 |
|---|---|
| **頁面** | 排桌管理 → 排桌工作區 |
| **功能** | `.sp-bar`（儲存排桌／同步／復原／重做／統計） |
| **現況** | `.sp-bar`（`admin.css:718`）**沒有 sticky**；≤960px 時 `.sp-pool` 也改成 `position:static`（`:1089`）。<br>所以手機上流程是：捲到最上面看未安排 → 往下捲找桌位 → 點卡片 → 移動 → **再捲回最上面按儲存**。一場 30 桌的婚禮，這條路要走幾十遍。<br>草稿只活在記憶體：`dirty` 旗標 + `beforeunload`（`seating-plan.js:2494`），undo/redo stack 也是純記憶體，**只有 `seatPlan.tagOrder` 存進 localStorage**（`:1781`）。iOS Safari 背景分頁被記憶體回收時 **不會觸發 `beforeunload`** → 整個下午的排桌無聲消失。 |
| **建議** | 1. **手機把儲存做成 sticky bottom bar**：`position:sticky; bottom:0`（或 fixed + `env(safe-area-inset-bottom)`），只留「儲存排桌」＋一個小小的「未安排 N 位」，其餘（同步／復原／重做／四個統計）收進「⋮ 更多」。注意要留出高度給 `.ad-toast-stack`（`bottom:26px`）不要互相蓋住。<br>2. **加本機草稿**：每次 `dirty=true` 時 debounce 1–2 秒把 `planPayload()` 寫進 `localStorage`（以 siteId 分隔）；下次進來若偵測到比雲端新的草稿，顯示「上次有一份還沒存的排桌，要接續嗎？」。<br>3. 補 `visibilitychange` → 頁面切到背景時先寫一次草稿（`beforeunload` 在行動裝置不可靠）。 |

## 2. P1 — 高

### P1-1｜觸控目標普遍過小、且相鄰的「編輯／刪除」容易誤觸

| 項目 | 內容 |
|---|---|
| **頁面** | 感謝信、故事牆、自訂內容、測驗題目、桌次名單、桌次圖、婚禮小卡、桌位管理、標籤庫 |
| **功能** | `.ad-edit` / `.ad-del` 行內動作、`.ad-chip` 篩選、`.ad-pager-btn`、`.sp-drawer-close` |
| **現況** | `.ad-del,.ad-edit{font-size:12px;padding:2px 0;}`（`admin.css:470`）→ **實際高度約 18px**，遠低於 44px。<br>`.ad-item-actions{gap:10px}` → 「編輯」與「刪除」只隔 10px，拇指一按很容易點錯（`admin.css:444`）。<br>桌位管理的 **↑ / ↓ 是單字元的 `.ad-edit`**（`seating-plan.js:1179`），寬度只有一個字，手機幾乎按不到。<br>`.ad-chip` 約 30px 高（`:348`）、`.sp-filters .ad-chip` 只有約 24px（`:818`）、`.sp-drawer-close` 約 24px、`.ad-pager-btn` 約 30px。 |
| **建議** | 1. `.ad-edit`/`.ad-del` 在 <900px 加 `min-height:44px; min-width:44px; padding:11px 12px;`（視覺上可維持無框，靠 padding 撐開熱區）。<br>2. **刪除與編輯不要並排**：手機把「刪除」移進每一列的「⋮」選單，或改成向左滑動顯示；至少把兩者間距拉到 16px 以上，並把刪除放在最右且加危險色。<br>3. ↑ / ↓ 改成 44×44 的方形按鈕；並依 P1-2 的建議一起改成「⋮ → 上移／下移／移到最前／移到最後」。<br>4. 所有 chip 在 <900px 提到 `min-height:36px`（篩選 chip 密度高，36px 是可接受的下限）。 |

### P1-2｜拖曳在觸控裝置完全失效，UI 卻仍在暗示「可以拖」

| 項目 | 內容 |
|---|---|
| **頁面** | 排桌工作區、測驗題目、桌次圖上傳、婚禮小卡上傳、當日流程、婚禮小卡清單 |
| **功能** | 拖曳排序 / 拖放上傳 |
| **現況** | ① **排桌**：`bindDnd()`（`seating-plan.js:1304`）用的是 HTML5 Drag & Drop，**觸控完全不會觸發**。`.sp-card{cursor:grab}` 只有在 `@media(max-width:960px)` 才改成 `pointer`（`admin.css:1095`）→ **iPad 橫向（1024px / 1194px）仍顯示 grab 游標、桌卡標題也是 `cursor:grab`，但拖不動**。替代路徑（點卡片 → peek → 「移動到桌位」）是有的，但完全沒有被說明，第一次用的人只會覺得壞掉。<br>② **桌位順序**：只能拖曳桌卡標題；`桌位管理` 分頁有 ↑↓ 可以替代（好），但工作區裡沒有任何提示告訴使用者「順序去那邊改」。<br>③ **測驗題目**：`setupQuizDrag()`（`admin.js:3151`）用 Pointer Events，手機可以拖（good），但 **沒有邊緣自動捲動** → 50 題時要把第 40 題拖到第 1 位是做不到的；也沒有任何「上移／下移／移到最前」的替代。<br>④ **當日流程**（`admin.js:2485`）：文案明說「由上到下就是大廳時間軸的顯示順序」，但 **完全沒有排序工具**，要調順序只能整列重打。<br>⑤ **婚禮小卡 / 桌次圖**：清單只顯示唯讀的 `#order`（`admin.js:2639`），**完全無法重新排序**。<br>⑥ 上傳區文案「點這裡選圖片，**或把圖片拖進來**」（`admin.html:499`、`:853`）在手機上是無效資訊。 |
| **建議** | 1. **每一個可排序的清單都補「⋮ → 上移／下移／移到最前／移到最後／移到第 N 個」**，這是本專案最缺的一塊。拖曳保留給桌機，觸控主打選單。<br>2. **排桌工作區**：<br>　・把 `cursor:grab` 與桌卡標題的拖曳提示改成用 `@media (hover:hover) and (pointer:fine)` 判斷，而不是用寬度斷點 → iPad 橫向就不會出現假的拖曳暗示；<br>　・在工作區頂部（或第一次進來的引導卡）明寫「手機／平板：點賓客卡 → 移動到桌位」；<br>　・每張賓客卡右側直接放一顆 44px 的「移動」小圖示，不要逼使用者先開 peek（現在是 2 tap 才碰得到移動）。<br>3. **測驗題目**：拖曳時加邊緣自動捲動；並補上「移到最前／最後」。<br>4. **當日流程**：每列補 ↑↓（44px），或直接支援 Pointer Events 拖曳把手（可沿用 `.ad-drag-handle` 的實作）。<br>5. **婚禮小卡／桌次圖**：至少讓 `#order` 變成可編輯的數字欄位，或補 ↑↓。<br>6. 上傳區文案改成響應式：`<900px` 顯示「點這裡選照片」，桌機才加「或把照片拖進來」。<br>7. 排序完成後除了 toast「順序已更新」，再補一個 **可 Undo 的 toast**（`showToast` 已支援 `actionLabel`，可直接沿用 `scheduleUndoDelete` 的模式）。 |

### P1-3｜Modal / Drawer 沒有背景鎖捲、沒有接上返回鍵、抽屜蓋住漢堡鈕

| 項目 | 內容 |
|---|---|
| **頁面** | 全站的彈窗與抽屜（確認框、自訂內容、感謝信、故事牆、測驗、桌位、匯入精靈、標籤權重、移動到桌位、賓客詳細抽屜、側欄抽屜、裁切器） |
| **功能** | `.ad-modal-mask`、`.sp-drawer`、`.ad-side`、`.cr-mask` |
| **現況** | ① **沒有任何 body scroll lock**（全專案只有 `common.js:1142` 一處 `body.classList`，與此無關）→ 彈窗開著時背景照樣捲，iOS 上關掉之後停在完全不同的位置。<br>② **返回鍵不會關彈窗**：`openDrawer()`／各 modal 都沒有 `history.pushState`（`admin.js:630`）→ 使用者在手機上直覺按返回，結果是 **跳到上一個分頁、甚至直接離開後台**，正在填的表單全沒了。<br>③ **側欄抽屜蓋住漢堡鈕**：`.ad-side` 開啟時 `position:fixed; top:0; z-index:1000`（`admin.css:110`），而 `.ad-bar` 是 `z-index:950` → 抽屜的不透明底色蓋住左上角的漢堡鈕，而 **抽屜裡沒有任何關閉鈕**，只能點右側遮罩或按 Esc（手機沒有 Esc）。<br>④ Bottom Sheet 一律是置中 modal，沒有下滑關閉的手勢。 |
| **建議** | 1. 開彈窗／抽屜時鎖背景：記下 `window.scrollY` → `body{position:fixed; top:-Ypx; width:100%}`，關閉時還原（iOS 上 `overflow:hidden` 不夠）。<br>2. 開啟時 `history.pushState({modal:id})`，監聽 `popstate` 關閉 → **返回鍵＝關閉彈窗**，符合 Android 與 iOS 邊緣手勢的預期。<br>3. 抽屜左上角補一顆 44px 的「✕」；或把 `.ad-side` 的 `padding-top` 讓出頂列並把 `.ad-bar` 的 `z-index` 提到 1010，讓漢堡鈕維持可按（變成 toggle）。<br>4. 手機（<560px）把 `.ad-modal-card-form` 改成 bottom sheet：`align-items:flex-end`、`border-radius: 12px 12px 0 0`、上緣加一條 drag handle，支援下滑關閉。 |

### P1-4｜出席回覆總覽在載入中會顯示假的「0」

| 項目 | 內容 |
|---|---|
| **頁面** | 出席回覆 → 出席回覆總覽 |

### P1-5｜收禮統計的大數字會在手機爆版

| 項目 | 內容 |
|---|---|
| **頁面** | 收禮小幫手 → 收禮統計 |
| **功能** | 禮金總額 `.ad-hero-num`（`admin.css:281`、`admin.js:3335` 的 `money()`） |
| **現況** | `font-size:clamp(52px,16vw,84px)`，且沒有 `word-break` / `overflow-wrap`。<br>390px 的手機上字級是 62px，`$1,280,000`（10 個字元、serif 數字約 0.55em）需要約 340px；而容器可用寬度是 390 − 32（`.ad-main` padding）− 44（`.ad-hero-stat` padding）＝ **314px** → **溢出並被 `body{overflow-x:hidden}` 切掉**。<br>台灣一場婚禮禮金破百萬很常見，這不是邊緣案例。 |
| **建議** | 1. `.ad-hero-num` 改成 `font-size:clamp(34px, 11vw, 84px)` 並加 `overflow-wrap:anywhere; line-height:1.1;`。<br>2. 更好的做法：金額用 `font-size: clamp()` + `letter-spacing:0` + `font-variant-numeric:tabular-nums`（已有），並在字數 >8 時自動降一級。<br>3. 破百萬時考慮顯示「$128.0 萬」，完整數字放在下方 `ad-hero-sub`。 |

## 3. P2 — 中

### P2-1｜圖片上傳失敗的原因說不清楚，HEIC 會被當成「使用者取消」

| 項目 | 內容 |
|---|---|
| **頁面** | 桌次 → 桌次圖；婚禮小卡；故事牆；婚禮資訊 → 交通資訊圖片 |
| **功能** | `uploadFiles()`（`admin.js:1687`）、`uploadCards()`（`:2555`）、`cropImage()`（`cropper.js`） |
| **現況** | ① 桌次圖失敗只給一句 **「上傳 N 張，M 張失敗（可能是檔案太大或格式不支援）」**——不說是哪一個檔案、也不說到底是哪一種原因（真正的錯誤只有 `console.warn`）。<br>② `cropImage()` 在 `img.onerror` 時 `resolve(null)`（`cropper.js:40`），與「使用者按取消」走同一條路 → **HEIC 解不開時被算成「略過」**，toast 說「已加入 3 張（略過 2 張）」，使用者完全不知道發生了什麼事。<br>③ `accept="image/*"` 沒有列 `.heic/.heif`；而 `f.type.startsWith('image/')` 會把 **MIME type 為空的檔案靜默濾掉**（從 iOS「檔案」App 選 HEIC 時很常見），只丟一句「請選圖片檔」。<br>④ **失敗後沒有「重試這幾張」**，只能整批重來。<br>⑤ 進度只有文字「處理中… 3 / 8」，沒有進度條；裁切確認到下一張裁切框之間的 Firestore 寫入（弱網可能好幾秒）**完全沒有指示**。<br>⑥ 上傳區已寫明 JPG／PNG／WebP 與「一張最多約 900KB（會自動壓縮）」（`admin.html:500`）——**這點做得好**，格式與大小限制清楚。 |
| **建議** | 1. 收集每一個檔案的失敗原因，結束後列出「`IMG_1234.HEIC`：這個格式瀏覽器讀不開，請在 iPhone 設定 →相機→格式 改成『最相容』後重拍，或先轉存成 JPG」。<br>2. `cropImage()` 改成 **decode 失敗 reject（或 resolve 一個 `{error}`）**，不要和取消混在一起。<br>3. `accept` 補 `image/heic,image/heif,.heic,.heif`；檔案過濾改成 `f.type.startsWith('image/') || /\.(heic|heif|jpe?g|png|webp)$/i.test(f.name)`。<br>4. 失敗清單旁邊放「重新上傳這 2 張」。<br>5. 進度改成 `<progress>` 或細長條，並在 Firestore 寫入期間顯示「儲存中…」。<br>6. **手機一定要實測這一條**：相簿 →選圖 →回到瀏覽器 →裁切 →上傳 →預覽。iOS 從相簿選大量照片回來時，分頁常常已經被系統回收重載，`<input type=file>` 的選取會整批消失。 |

## 5. 建議的處理順序

**第一批（一週內，改動小、收益最大）**

1. 所有輸入元件 `font-size: 16px`（<900px）——一行 CSS，直接解掉 iOS 自動放大（P0-1）
2. `.ad-edit`/`.ad-del`/`.ad-chip` 補 `min-height:44px`（<900px）（P1-1）
3. `renderRsvps()` 的 `loadedOnce` 檢查移到最前面（P1-4）
4. `.ad-hero-num` 加 `overflow-wrap` 並調 clamp 下限（P1-5）
5. `.ad-subtabs` 加左右漸層遮罩（P2-4）
6. `88svh` → `88dvh`、viewport 加 `interactive-widget=resizes-content`（P2-6）
7. 上傳區文案響應式化、`accept` 補 HEIC（P2-1）

**第二批（兩週，需要一點邏輯）**

8. 儲存按鈕的 `disabled` + 「儲存中…」+ 8 秒逾時 toast（P0-2 的前半）
9. 全域斷網橫幅（P0-2 的後半）
10. 彈窗／抽屜的 body scroll lock ＋ `history.pushState`（P1-3）
11. 排桌工作區 sticky bottom save bar（P0-4 的前半）
12. 篩選條件彙總列 ＋ 清除（P2-3）

**第三批（需要設計）**

13. 回覆名單、收禮明細的手機 Card View（P0-3、P2-7）
14. 各清單的「⋮ → 上移／下移／移到最前」（P1-2）
15. 長表單與排桌的 localStorage 草稿（P0-4 的後半、P2-5）
16. 斷點策略從寬度改成 `hover`／`pointer`（P2-8）
