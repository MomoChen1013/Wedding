# 後台「表單設定」UX Review ＋ 改版記錄

> 對象：新人後台 `/w/{slug}/admin` 的側欄分頁「**表單設定**」。
> 這份文件寫的是**現在程式碼裡真的長這樣**：先是改版前的問題盤點，
> 再是實作後的資訊架構、Component 對照與互動流程。
> 視覺規格本身在 `docs/UI-SPEC.md`（新元件見 3.5b／3.6b／3.6c／3.6d）。

---

## 0. 一句話

改版前這一頁是**一串從頭排到尾的勾選框**，所以新人回答不了三個問題：

> 「這個設定會影響誰？」「這個問題什麼時候會出現？」
> 「我現在改的是全部活動，還是只有這一場？」

改版後每一組的**標題就回答了第一個問題**，Conditional Reveal 回答第二個，
「全域 ／ 僅此場次」的兩層 ＋ Badge 回答第三個。

## A. 改版前的 UX 問題

| # | 問題 | 為什麼會造成誤解 |
|---|---|---|
| A1 | **同一頁三種不同層級的設定長得一模一樣** | 「每個活動各自要問的」「整份回覆只問一次的」「表單資訊」三組都是 `.ad-check` 一路排下來。新人分不出哪一項只影響一場、哪一項影響全部 |
| A2 | **沒有「所有場次」這一層** | 四題的開關只存在 `events[].ask*`。多活動時要一場一場勾；而畫面上看不出「這四題其實問的是同一件事」 |
| A3 | **改一場看起來像改全部（反之亦然）** | 取消某一場的「餐點分配」之後，畫面上沒有任何標記。三個月後回來看，無法判斷這是「我們不問餐點」還是「只有證婚不問」 |
| A4 | **活動設定散在兩個分頁** | 時間地點在「婚禮資訊 → 其他流程」、要問什麼在「表單設定」、要不要回覆又在「其他流程」。改一個活動要在兩頁之間來回，回來還得再找到剛剛那張卡 |
| A5 | **同一件事給了兩個入口** | 「需要賓客回覆」在其他流程；「這個活動目前會問什麼」也在其他流程（唯讀），但開關在表單設定。兩邊的說明各寫一次，一改就對不起來 |
| A6 | **自訂題目全部欄位一開始就攤開** | 題目、題型、選項、提示同時出現在一列裡，而且只有「單選／文字」兩種。選項固定兩格、上限 4 個，加減都要在同一片密集的欄位裡進行 |
| A7 | **郵寄用 Checkbox** | 它開的不是「一題」，是**一整段**（喜帖多一個選項、喜餅多一個選項、選了才問地址）。和「要不要問喜餅」用同一個元件，看起來像同一個量級的決定 |
| A8 | **條件顯示只寫在說明文字裡** | 「打勾時會多一個郵寄…」「選了才會問地址」全部靠 `.ad-hint` 描述。設定的結果看不見，只能讀 |
| A9 | **聯絡方式可以三種都不勾** | 送出去的回覆會完全沒有聯絡方式，而畫面上只有一句「三種都不勾就整題不問」。錯誤在送出之後才發生 |
| A10 | **「其他備註」是固定題目** | 它和「想對新人說的話」問的是同一件事的兩個口氣，卻只有後者關得掉 |
| A11 | **只有「查看表單」一顆按鈕** | 新人最常做的事是把連結傳給賓客，那反而沒有入口；而「查看表單」同頁開啟，會把正在編輯的設定頁蓋掉 |

## B. 新舊資訊架構比較

### 改版前

```
表單設定
├─ 1 每個活動各自要問的      （多活動才出現）
│   └─ 一個活動一組勾選框：人數／餐點／兒童椅／飲食
├─ 2 題目（或「整份回覆只問一次的」）
│   └─ 固定題目 8 條 ＋ 喜帖 ＋ 喜餅 ＋ 想說的話
│       ＋ 郵寄（Checkbox）＋ 聯絡方式
└─ 3 表單資訊（唯讀）

婚禮資訊 → 其他流程
└─ 活動卡（時間、地點、說明）
    ＋ 需要賓客回覆（Checkbox）
    ＋ 這個活動目前會問（唯讀複製一份）
    ＋ 追加題目（欄位全開）
```

問題：**同一個活動被切成兩半**，而且「層級」這件事完全沒有被畫出來。

### 改版後

```
表單設定                         [複製表單連結] [預覽 ↗]
├─ ① 活動場次
│   ├─ 所有場次的基本問題        ← 只有 ≥2 個要回覆的活動才出現
│   │   能來參加嗎（系統固定）／出席人數／餐點分配／兒童座椅／飲食習慣補充
│   │   每一列右邊：已套用 N/M 個場次｜某場次單獨停用
│   └─ Activity Card ×N（含不需要回覆的場次，整張淡出）
│       ├─ 活動基本資訊：種類 Badge・日期・時間・地點   [編輯活動資訊] → Modal
│       ├─ ☑ 需要賓客回覆
│       ├─ 基本問題：來自所有場次｜僅此場次停用 ＋「恢復所有場次設定」
│       └─ 本場次專屬問題：Question List（拖曳排序／編輯／刪除）＋ 增加自訂題目 → Modal
├─ ② 必填基本資料（不分活動，關不掉）
│   怎麼稱呼你？／與新人的關係？＋ 選項 Chips 預覽
│   是哪一種關係（＝賓客標籤）＋ 新增關係標籤 → Modal
│   聯絡方式：電話／LINE／Email（至少一種，最後一個關不掉）
├─ ③ 喜帖／喜餅（不分活動，填一次）
│   ☑ 喜帖領取方式 → Reveal：選項預覽
│   ☑ 喜餅領取方式 → Reveal：選項預覽
│   郵寄服務（Switch）→ Reveal：會多出來的選項與收件地址
├─ ④ 其他資料：☑ 想對新人說的話　☑ 其他備註
└─ ⑤ 表單上的其他內容（唯讀，內容在「婚禮資訊」填）

婚禮資訊 → 其他流程
└─ 活動卡（時間、地點、說明）＋ 一句「要問什麼在表單設定」
```

### 資料層：兩層開關

| 層 | 存在哪 | 意思 |
|---|---|---|
| 全域 | `sites.rsvpAskCount／rsvpAskMeal／rsvpAskChildSeat／rsvpAskDiet` | 這場婚禮**到底要不要**收集這項資料 |
| 單一場次 | `events[].askCount…`（既有欄位） | 這一場要不要**少問**一題（只能往下關） |

效果值＝`全域 && 這一場`，收斂在 `common.js` 的 `eventAsks()`／`rsvpEventsAsked()`，
賓客表單與後台統計讀的都是它。**後台編輯時讀的仍然是 `events[]` 原本那一份**
（override 本身）—— 不然全域一關，個別場次的設定就會被效果值覆蓋掉。

單一場次的站台（只有一個要回覆的活動）**看不到第二層**：
勾選框同時寫全域與那個活動，兩邊永遠一致。「簡單婚禮不能被複雜化」。

## C. Component Mapping

| 功能 | 元件 | 為什麼 |
|---|---|---|
| 出席人數／餐點分配／兒童座椅／飲食習慣補充 | **Checkbox** `.ad-check` | 問的是「要不要收集這項資料」 |
| 喜帖領取方式／喜餅領取方式 | **Checkbox** | 同上，一題就是一列 |
| 想對新人說的話／其他備註 | **Checkbox** | 同上 |
| 電話／LINE ID／Email | **Checkbox**（複選，最後一個 disabled） | 「要收集哪幾種」是複選；至少一種是規則，所以用 disabled 表達而不是等送出才報錯 |
| 需要賓客回覆 | **Checkbox** | 它決定「這一場要不要收集回覆」，仍然是收集與否 |
| 提供喜帖／喜餅郵寄 | **Switch** `.ad-switch` | 開的是一個**服務**：開了會長出郵寄選項與收件地址整段 |
| 題型：單選／多選／簡答題 | **Radio group** `.ad-radios` | 三個模式只能選一個 |
| 怎麼稱呼你？／與新人的關係？／聯絡方式／能來參加嗎 | **Disabled Checkbox ＋ Badge「系統固定」「必填」** | 關不掉的題目要看得出「不是壞了，是本來就這樣」 |
| 男方親友／女方親友／雙方親友／其他 | **Chips 預覽**（`.ad-chips` 容器 ＋ 不可點的 `.ad-tag`） | 只是 Preview。可點的東西一定要有 hover 反應，`.ad-tag` 一個都沒有 —— 這就是它不會被當成可編輯的原因 |
| 喜帖／喜餅的選項、關係標籤 | **Chips 預覽** | 同上，而且內容直接從 `RSVP_OPTIONS` 長出來，和賓客看到的是同一份 |
| 來自所有場次／僅此場次停用／已套用 N 個場次／主要活動／系統固定 | **Badge** `.ad-badge` | 唯讀狀態。`.is-warn` 專門給「這一格和全域不一樣」 |
| 郵寄關閉時的郵寄項目與地址設定 | **Conditional Reveal** `.ad-reveal` | 沒有前提就沒有這一段（`hidden`，不是灰掉） |
| 喜帖／喜餅的選項預覽 | **Conditional Reveal** | 不問這一題時，它的選項不該還在畫面上 |
| 題型選了才出現的「選項」／「提示文字」 | **Conditional Reveal** | 一開始全部攤開，等於要新人先看懂三種題型的差別 |
| 編輯活動資訊 | **Modal** `.ad-modal-*` | 不跳頁（改版前最大的操作成本就是「回來找不到剛剛那張卡」） |
| 新增／編輯自訂題目 | **Modal** | 同上；題目有 5 個欄位，塞回列表裡會擠爆 |
| 新增關係標籤 | **Modal**（`promptModal`） | 只要一行輸入，沿用既有元件 |
| 自訂題目排序 | **Drag & Drop** `setupDragSort()` ＋ `.ad-drag-handle` | 沿用測驗題目那一份；觸控裝置另外從「⋮」走「上移／下移／移到最前／最後」 |
| 活動場次 | **Card** `.ad-actcard` | 一筆裡有名稱、時間、地點、開關、兩組題目，行高完全不一致（UI-SPEC 3.10 的判準） |
| 自訂題目 | **清單列** `.ad-qrow` | 一到兩行、右邊幾顆按鈕 |

**沒有新造的元件**：Modal、Drawer、Checkbox、Chip、Tag、卡片、清單列、
拖曳排序、`⋮` 選單、toast、undo 刪除、`confirmModal`／`promptModal`、
`registerFormModal`、`runSave` 全部沿用。新增的只有 Badge、Switch、
Radio group、Conditional Reveal 四個 —— 而它們是既有語彙裡真的缺的那四個。

## D. Interaction Flow

### D1. 修改全域基本問題（多場次）
1. 表單設定 → ①「所有場次的基本問題」取消「飲食習慣補充」
2. 立刻寫 `sites.rsvpAskDiet = false`，toast：「所有場次都不問這一題了」
3. 每一張活動卡上那一列**變成 disabled ＋ Badge「所有場次都不問」**
   —— 全域關了，個別場次開不回來（只能往下關）

### D2. 單一場次覆寫
1. 「婚宴」那張卡上取消「兒童座椅」
2. 只寫 `events[婚宴].askChildSeat = false`，**全域那一份一個字都不動**
3. 那一列出現 Badge`.is-warn`「**僅此場次停用**」＋「恢復所有場次設定」
4. 全域那一塊同一列出現「**婚宴單獨停用**」—— 兩邊互相指認
5. toast：「已在『婚宴』單獨停用，其他場次不變」
6. 按「恢復所有場次設定」→ 回到 `true`，Badge 變回「來自所有場次」

### D3. 新增場次專屬問題
1. 「婚宴」卡上「＋ 增加自訂題目」→ Modal
2. 填題目名稱 → Radio 選「多選」→ 下面才出現「選項」那一段（預設兩格，最多 8 個）
3. 儲存 → 寫進 `events[婚宴].questions`，toast，卡上長出一列
4. 「證婚」那張卡仍然顯示「尚未新增問題」—— 專屬就是專屬

### D4. 編輯／刪除／排序自訂問題
- 編輯：列上「編輯」或「⋮ → 編輯這一題」→ 同一個 Modal（已定下來的選項 id 不動，改字不會把已送出的作答對丟了）
- 刪除：`confirmModal` 說清楚「已送出的回覆仍然保留，只是這一題不再出現」
- 排序：拖曳把手；觸控裝置從「⋮」走上移／下移／移到最前／最後

### D5. 開啟郵寄服務
1. ③ 的 Switch 打開
2. Reveal 出現：喜帖多一個「郵寄」、喜餅多一個「郵寄」、選了郵寄才問收件地址
3. 喜餅的選項預覽同時多一顆「郵寄」Chip —— **還沒按儲存就看得到結果**
4. 按「儲存表單設定」才寫 `rsvpMailEnabled`（②③④ 是一張表單）

### D6. 關閉郵寄服務
1. Switch 關掉 → Reveal **整塊消失**（不是灰掉），預覽少一顆「郵寄」
2. 喜帖與喜餅兩題都取消時，「郵寄服務」整塊收起來 —— 沒有東西可以寄

### D7. 驗證至少一種聯絡方式
1. 取消電話、取消 LINE → 只剩 Email
2. Email 那一顆**自己變成 disabled**，hint 說「至少要留一種，所以現在勾著的這一種關不掉」
3. 勾回電話 → Email 解開
4. 舊站台曾經三種都關掉的情況：送出時 toast「聯絡方式至少要勾選一種」並把焦點帶到 Email

### D8. 編輯活動資訊
1. 卡上「編輯活動資訊」→ Modal（種類、名稱、日期、時間、地點、地圖、說明、需要賓客回覆）
2. 儲存 → 寫 `events[]`；主要活動的地點同時鏡像回 `sites.venueName／venueAddress／venueMapUrl`
3. toast：「活動資訊已更新，用到這個時間地點的頁面都會一起調整」
4. 婚禮資訊的場地三欄、其他流程那一頁、表單上方的資訊列一起重畫
5. 站台還沒有 `events[]` 時（80% 只辦一場婚宴的新人）：同一個 Modal 改的是
   `sites` 本身那幾欄與 `eventDate` 的「幾點開始」；日期仍然只有我們改得動

## E. 相容性（既有 RSVP 資料）

| 擔心的事 | 實際上 |
|---|---|
| 既有站台少了 `rsvpAskCount…` 這幾個欄位 | 一律「沒設定過就視為開著」（`rsvpConfig()` 的 `on()`），效果值＝`events[].ask*`，和改版前一模一樣 |
| 已經送出的回覆 | 一個字都不動。`events[].answers` 仍然是 `題目 id → 字串` |
| 多選題怎麼存 | 同一個字串欄位，用逗號串起選項 id。規則與 `answers` map 都不必改型別；顯示走 `questionAnswerText()`（單選就是一個元素的清單） |
| 舊的 `kind:'text'／'choice'` | 照原樣運作；`multi` 是新增的第三種，認不出來的一律當 `choice` |
| 選項上限從 4 變 8 | 只放寬，不影響既有資料 |
| `其他備註` 變成可關 | 預設 `true`（沒設定過就視為開著），既有站台的表單不會少一欄 |
| Firestore 規則 | 新增的五個欄位加進新人可寫的白名單並擋型別（`bool`）；`rsvpEnabled`／`rsvpDeadline` 仍然改不動 |
